## TL;DR

**不是「HTTP 比 RPC 快」，是「大块只读字节不该走控制通道」——而且省的是搬运那一段，省不到 Go 的组装。**

| 数据形状 | 走哪 | 本仓库现状 |
|---|---|---|
| 大块只读字节（图片、整条 transcript） | **asset server（HTTP）** | 图片 `e7bf3ee`；transcript **`b23f713`** |
| 小参数 + 有返回值的命令（`SetModel` / `Rename` / `Start` / `PickWorkspace`） | **RPC** | 全部 |
| 需要错误映射 / 真取消的调用 | **RPC** | 全部 |
| Go→JS 流式事件（`pi:event` / `terminal:event`） | **RPC 事件通道** | ⚠️ `terminal:event` 带 `dataB64`，见 §6 |

同一条会话、同一轮里交替实测（4575KB / 2112 条）：**桥 321ms vs HTTP 201ms → 省 ~120ms（39%）**。
换算下来桥的额外成本 ≈ **111ms / 4.6MB ≈ 24ms/MB** —— 不是几十倍，是三成。别拿这个数去做 1.39MB 以下的决策。

## 2 · 实测数字（2026-09-30，dev 沙箱，同一条 7.6MB / 2112 条会话；探针 `.pi/bin/hitprobe/devSwitchProbe.ts.keep`）

| 项 | ms | 探针步骤 |
|---|---|---|
| **端到端：桥**（store 全程，强制替换 transport） | **313 / 321 / 328** | `s7.e2e`（3 轮交替） |
| **端到端：HTTP**（同一轮交替测） | **199 / 201 / 202** | `s7.e2e` → `s7.e2e.median` 省 120ms |

| `mint` 用 `index.Resolve`（读整档建 summary） | **95** | `s0c.mint`（旧实现） |

| Go 侧独立基线：读盘 / jsonl→map / `Index.Snapshot` / Marshal / Unmarshal | 1 / 53 / 130 / 25(5.4MB) / 30 | `go test ./internal/sessionindex -run TestZZProbeSnapshotCost -v`（`session-cost.go.keep`） |

⇒ 冷开一条长会话现在约 `Go 组装 130-165 + HTTP 搬运 ~15 + JS parse 18 + 首次 apply ~160`。
**搬运已不是大头**；剩下能砍的是 Go 组装（F1 骨架）与首次 apply。

## 3 · 为什么桥更贵（机制，附可信度）

| # | 机制 | 依据 |
|---|---|---|
| 1 | **通道形态**：message handler 一条消息带一个可序列化值，为调用/事件设计，不为 4.6MB 载荷设计 | 高（`frontend/node_modules/@wailsio/runtime/dist/system.js` 第 17-29 行直接可见） |
| 2 | **编解码层数**：RPC 要把结果编码进一段注入的 JS 源码、主线程 eval、再解 envelope；HTTP 只解析一次 | 中-高（JS 侧与 Go 类型可见，**Go 侧注入实现未逐行读**） |
| 3 | **线程归属**：桥在 UI 进程主线程；HTTP 的接收/解码在 WebKit 网络进程 | 中（由帧间隔与本次 A/B 差值反推，未做线程 trace） |
| 4 | **`<img>` 白送**：图片那条收益主要不是「传输快」，而是**字节根本不进 JS**（原生解码 + 不进堆 + 不参与 parse） | 高（`e7bf3ee` 的代码与截图） |

⚠️ **作废一条旧结论**：09-29 记的「1.39MB：RPC 89ms vs asset server 4-6ms ⇒ 35-64ms/MB」是**无效对比** —— 89ms 是「整次快照打开」（含 Go 读盘+组装+解析+应用），4-6ms 是「单张图片一次 fetch」。今天同轮交替实测的真实桥开销是 **≈24ms/MB**。

## 4 · Wails RPC 的优势（别为了性能丢）

| 优势 | HTTP 换不来的原因 |
|---|---|
| 类型化绑定 | `domain$0.SessionSnapshot` 由 Go 结构体生成；HTTP 要手写 DTO |
| 错误语义 | Go 的 `error` 自动映射成 `RuntimeError`/reject（`frontend/node_modules/@wailsio/runtime/dist/calls.js` 第 46 行） |
| **真取消** | `oncancelled` 会向 Go 发 `cancelCall`；`AbortController` 只断连接 |
| 命令类调用 | `Start`/`Stop`/`Write`/`PickWorkspace`（弹原生面板）没有 HTTP 对应物 |
| 不暴露网络面 | 桥只有本进程 webview 能调；asset server 一开路由就是本机 HTTP 面 |
| **小消息更省** | 一次 handler 往返是常数；HTTP 有请求行/头/中间件链 —— 所以 `SessionSnapshotRef` 这种几十字节的调用**该走桥** |
| 跨平台一致 | `frontend/node_modules/@wailsio/runtime/dist/system.js` 第 17-29 行 同一份绑定跑 Win/mac/Android |
| Go→JS 事件流 | `Events.On(...)` 开箱即用 |

## 5 · 走 HTTP 要付的代价 + 两个实测踩到的坑

1. **ref 不可伪造**：`base64url(payload).base64url(hmac-sha256)`，per-process key（`internal/sessionindex/imagerefs.go:48` 生成、`internal/sessionindex/imagerefs.go:58` 铸造、`internal/sessionindex/imagerefs.go:71` 解析；transcript 侧 `internal/sessionindex/transcriptrefs.go:53` 与 `internal/sessionindex/transcriptrefs.go:78`）
2. **路径复校验**：解析回来仍要过 `ValidatePath`（sessions root 内 + `.jsonl`）
3. **内容会变**：transcript 的 ref 里钉了 **mtime+size**，会话一写就 stale → 404 → 调用方重新 mint 或退回桥；不能拿旧 ref 当"当前正文"
4. **⚠️ 坑一：mint 不许读文件。** 守卫要用 `index.Header`（只读首行）而不是 `index.Resolve`（读整档建 summary）。后者实测 **95ms**，正好把这次要省的 120ms 全吃回去 —— 第一版就是这么写的，实测才暴露
5. **⚠️ 坑二：`wails://` 不吃 HTTP 缓存。** 同一 ref 第二次 fetch 实测 327ms，`immutable` 只是正确性声明。**任何"重开就免费"的设计都别基于它**
6. 过期一律答 404 不答 403（`internal/appservice/sessionimage.go:57-62` 的注释）：让前端的兜底分支保持无聊
7. 只读 + 限方法：`GET/HEAD` only
