# Reader views

Two independent render paths, one dispatch point (`InspectorPanel.vue`, `readerDocument`).

| Format | Engine | Why |
|---|---|---|
| PDF | `pdfjs-dist` 6.x, rendered by this directory | Range loading, per-page render, zoom cache — none of which a wrapper gives us |
| EPUB | `foliate-js` `view.js` only | Lazily reads zip entries (`blob.slice`), pages by CSS columns + transform |

`foliate-js` also ships a PDF adapter, but it is **not published to npm** and pins its own copy of
pdf.js. `view.js`'s `makeBook` dispatches on the file's magic (zip → EPUB) and never imports that
adapter, so keeping PDF out of foliate-js needs no patch at all.

## Which WebView can run this

`MACOSX_DEPLOYMENT_TARGET` is `12.0` (`build/darwin/Taskfile.yml`), so macOS 12 runs WKWebView 15.x.
Nothing in this directory can raise that floor — `build.target: "safari15"` plus `polyfills.ts` are
what keep the app loadable there. Three things had to be handled, and every one of them was found by
running the engine in WKWebView, not by reading a changelog:

1. **`static {}` class blocks** in pdf.js (`Safari 16.4`). Syntax — no polyfill exists. Transpiled by
   `build.target`, and by `worker.rolldownOptions.transform.target` for the worker, which does *not*
   inherit `build.target`. Verify: `grep -c "static{" dist/assets/*.js` must be 0.
2. **`Map`/`WeakMap.prototype.getOrInsertComputed`** (TC39 upsert, in no shipping WebKit). pdf.js
   calls it 40 times; without it `PDFPageProxy.render` throws before drawing anything. Patched in
   `polyfills.ts` for both prototypes — `CanvasGraphics.#pathCaches` is a `WeakMap`.
3. **Regex lookbehind** in `foliate-js/paginator.js`. A lookbehind is a *parse* error on WebKit 15 and
   no bundler lowers it, so `src/utils/safari15Compat.ts` rewrites the one expression at build time.
   Verify: `grep -r "(?<[=!]" dist/assets` must be empty.

`polyfills.ts` is imported by `pdfEngine.ts` and by `pdfWorkerEntry.ts`, so the worker is patched too
— patching the window alone is not enough, every page is decoded in the worker.

## Vendored CSS

`src/styles/pdf-text-layer.css` is extracted from `pdfjs-dist@6.5.438/web/pdf_viewer.css`
(Apache-2.0). The package does not ship the standalone `text_layer_builder.css` the pdf.js repo has,
and importing the whole 165KB viewer stylesheet would restyle the app. Re-extract after an upgrade:

```bash
cd frontend && python3 - <<'PY'
src = open('node_modules/pdfjs-dist/web/pdf_viewer.css').read()
blocks, depth, start = [], 0, 0
for idx, ch in enumerate(src):
    if ch == '{':
        if depth == 0: start = idx
        depth += 1
    elif ch == '}':
        depth -= 1
        if depth == 0:
            head = src.rfind('}', 0, start) + 1
            if '.textLayer' in src[head:start]:
                blocks.append(src[head:idx + 1].strip())
print('\n'.join(blocks))
PY
```

The extraction keeps only `.textLayer` blocks, but the font-size chain needs `--total-scale-factor`,
which upstream declares on `.pdfViewer .page` — **re-add it to the vendored `.textLayer` block after
every re-extract**, otherwise the transparent spans fall back to the inherited font-size and text
selection highlights the wrong lines:

```css
.textLayer { --total-scale-factor: calc(var(--scale-factor) * var(--user-unit)); }
```

## Untrusted book content

`foliate-js` renders a section in a same-origin iframe whose sandbox includes `allow-scripts`, and
`epub.js` deliberately keeps inline `<script>` elements (`allowScript` only blocks manifest JS).
Every book is therefore treated as hostile before its markup reaches the iframe:

- `src/utils/foliateCsp.ts` rewrites `epub.js` at build time: it removes `<script>`, `on*` handler
  attributes, `<base>` and `<meta http-equiv="refresh">`, then prepends a CSP `<meta>` to the
  section head;
- `buildContinuousDocument()` adds the same CSP to the merged document used by continuous pagination;
- the policy allows only blob/data images, fonts, media and stylesheets, and closes scripts,
  frames, objects, connections, forms and `<base>`.

`vite.config.ts` fails the build when the `epub.js` source no longer matches the rewrite, so a
foliate-js upgrade cannot silently reopen the same-origin script path. A hostile fixture (inline
script + remote `<img>`) must leave `parent.__pwned` false and produce no remote request; the
positive control is the same markup in a plain sandboxed iframe, which does execute.

## Engine assets

`public/pdf/` is generated by `scripts/copy-pdf-assets.mjs` (run from `predev`/`prebuild`) and is
gitignored: `cmaps` (CJK text without a ToUnicode map), `standard_fonts`, `wasm` (JPEG-2000, JBIG2,
colour profiles) and `iccs`. ~4.2MB on disk; each file is fetched only when a document asks for it.
`wasmUrl`/`iccUrl` are **not optional** — without them a scanned book renders blank pages with no
error to show for it.

## Verification recipe (Tier B)

A page that imports `/src/readers/pdfEngine.ts` from the vite dev server, opens a real PDF, renders
page 1 and counts non-white pixels, proves more than any unit test here can: worker construction,
asset URLs, canvas, and the text layer. Same for `foliate-js/view.js` → `open()` → `columnWidth`.
`.pi/bin/hitprobe/hitprobe.swift` is the model for driving a real WKWebView; for this use
`callAsyncJavaScript` so an async probe can be awaited.
